## 已完成的基础

- 轻量客户端先以文字模式游玩，资源包下载、认证解密后保存到本机，后续启动复用。
- 资源面板提供“全部下载”、总进度和暂停。单包与全部下载共用缓存检查，重试跳过已完成分卷，正在传输的未完成分卷重新下载。
- 天庭、奇妙工具及其专属资源已移除。
- 资源采用 AES-256-GCM 加密，源码和公开资源仓库不保存实际密钥。客户端携带解密材料，这层加密不能阻止取得客户端的人提取资源。
- `C3nHx/noname` 已配置 Actions secret `NONAME_RESOURCE_KEY`，各平台正式构建可以复用同一资源密钥。
- 发布源与实际下载地址可以分开配置。OSS 直接下载时，`NONAME_RESOURCE_BASE_URL` 指向 OSS 版本目录，无需设置独立分发覆盖地址。
- 已增加官方 SDK 的 OSS 发布脚本，按禁止覆盖、匿名回读验证和最后发布清单的顺序执行。
- 已配置 `NONAME_RESOURCE_ROOT_URL` 仓库变量，各平台工作流在构建时自动追加当前版本目录。
- 网页打包新增的启动脚本已纳入核心缓存，打包后的启动内容变化会更新核心构建标识。
- 带 HTTP Basic 认证的部署公开三个无密钥 Worker 引导脚本，解决注册请求 401 导致缓存图片无法读取的问题。页面、解密配置和文件接口继续要求认证。

当前分支版本为 `1.11.7-c3nhx.4`，全部下载与 OSS 复制实现提交为 `4aef7d90`。随后已发布 [GitHub Release](https://github.com/C3nHx/noname/releases/tag/v1.11.7-c3nhx.4)，并通过独立 Actions 生成轻量测试签名 APK。

## .4 APK 下载 404 的修复

实际 APK 使用 OSS `.4` 根地址，密钥、21,527 个素材哈希和分卷划分均与本地发布一致，但 84 个分卷文件名全部不同。已复现 APK 引用的 84 个地址均返回 404。原因是固定 UTC 日期被 JSZip 转为构建机器的本地 DOS 时间；GitHub 的 UTC 构建与本地上海时区构建生成了不同 ZIP 哈希。

已按 APK 清单重建并补发 84 个分卷，逐卷匿名回读和认证解密通过，原公开清单及网页分卷保留。补发收据为 `.audit/oss-apk-compatibility-v4.json`。复查实际 APK 全部地址为 200；直接运行 APK 内下载、解密模块，卡牌包的 361 个文件下载与逐文件校验通过，再次检查不重复下载。此验收未连接用户手机。

源码已固定 ZIP DOS 时间，并通过 `archiveVersion: 1` 避免继续复用旧格式缓存。52 项测试覆盖跨时区一致性和兼容补发边界。已安装的 `.4` APK 可以直接重试下载，不需为本次修复更换安装包。

## 全量缓存后的网页启动错误

用户截图显示 Edge 网页在下载素材、启用美术并重启后，报 `Failed to execute 'keys' on 'Cache': Operation too large`。已在真实 Edge 中用 21,527 条缓存复现。初始化不再调用 `Cache.keys()`，改为按下载状态、每批最多 32 项检查单个缓存键；丢失记录从状态中移除，其余缓存保持可用。

同一浏览器 profile 保留原缓存后，重启核验成功，21,527 个文件记录全部可用。53 项测试覆盖大量缓存枚举失败、缺失资源回退和原有下载行为。修复已部署到阿里云，线上文字对局、OSS 下载和重启复用通过。

旧启动缓存仍报错时，可在同一浏览器打开 `resource-recovery.html`，只更新启动文件。线上恢复验证先建立会触发旧枚举错误的 21,527 项缓存，再执行恢复，确认新核心启动、缓存数量和 IndexedDB 设置均保留。该页面是无密钥的独立恢复工具，允许匿名读取；游戏页面及解密配置仍要求认证。

## APK 全量素材后的启动阻塞

实际 `.4` CI APK 在隔离模拟器中使用原生存储，与网页缓存枚举错误不同。保留 21,527 个真实素材及其下载状态后，跟踪到 `resources.attach()` 等待逐文件核验，期间界面为空白。私有目录使用 `DocumentFile.findFile()` 逐段查找，每次重新枚举同级文件，音频大目录会产生重复扫描。

已将 file URI 的私有目录查询改为直接构造文件路径并检查存在性。SAF 的 content URI 继续使用原查询。测试包保留 CI APK 的游戏核心文件与原素材，覆盖安装到隔离实例后，全量核验完成、美术与扩展启用、8 人对局推进和卡牌响应哈希均通过，原文件系统 3 项仪器测试通过。证据保存在 `.audit/native-fixed-restart-result.json`、`.audit/native-full-art-result.json` 和 `.audit/native-filesystem-fixed.log`。这证明修复覆盖了复现的原生阻塞，尚未连接用户手机验证。

修复提交 `724e5048` 已推送；[更新 APK 构建](https://github.com/C3nHx/noname/actions/runs/42627732468)成功，产物仍是测试签名，Actions 保留 3 天。实测旧 `.4` APK 证书 SHA-256 以 `cbb153d7b8b2` 开头，新包以 `a16ecad26b8f` 开头，不能保留数据覆盖安装。当前仓库未配置 Android 发布签名 secret，不把测试构建视为稳定升级链路。保留用户当前安装和素材；后续需要恢复原签名材料，或在用户确认的数据迁移方案下建立固定签名版本，不能要求用户通过卸载解决本次启动问题。

## 网页完整离线启动的独立遗留

本轮新增验证了“关闭浏览器进程后，禁用网络再打开网页”。该流程出现启动失败，已定位到 `noname/util/sandbox/sandbox.js` 的加载请求。它属于核心文件，由 `initRealms.js` 创建的独立 iframe 加载，重启后该请求未从既有核心缓存返回。失败表现为加载内容失败的 `[object Event]` 提示。

在线文字对局、下载资源后的在线进程重启复用和已缓存图片的离线读取已通过。完整离线启动需后续处理沙盒启动依赖，不能由这些资源缓存结果推断为已支持。当前 OSS 接入不修改沙盒隔离机制。

## 选择 OSS 前保留的三个方案

以下保存此前讨论的方案与限制。当前采用 OSS 直接发布，不再执行从 CNB 同步到下载站的双重发布流程。

| 方案                      | 实施内容                                                             | 使用体验                                 | 成本与限制                                                               |
| ------------------------- | -------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------ |
| 独立 OSS、COS 或 CDN 分发 | 将加密分卷和公开清单发布到支持 HTTPS、CORS 的版本目录                | 网页内下载并缓存，资源流量不经游戏服务器 | 已采用 OSS 直出；不再经由 CNB 复制，CDN 未接入，产生存储、请求和出网费用 |
| 阿里云服务端转发          | 游戏站点的服务端读取 CNB，向浏览器流式返回密文，限定允许的版本和文件 | 可在网页内自动下载，CNB 继续保存源文件   | 资源流量仍经过现有服务器出口，不能解决原有小带宽瓶颈；尚未实现           |
| CNB 手动下载后导入        | 浏览器跳转下载 `.nrp`，客户端提供本地导入、解密、校验和缓存入口      | 首次多一步手动操作，导入后可复用缓存     | 不需要另建下载服务，但本地资源包导入功能尚未实现                         |

用户已开通 OSS 并提供 Bucket，选择对象存储直接下载。自定义资源域和 CDN 可按后续实际需要增加，当前不创建其他付费服务。

仅返回 CNB 重定向地址不列为第四种方案。最终文件域同样拒绝外站 Origin，这条路径已实测失败。

## 恢复工作

1. 按 [上游与资源发布 skill](../.agents/skills/noname-upstream-release/SKILL.md) 核对源码、版本、原资源密钥与本地构建。保留 CNB 历史收据，不再补发其清单。
2. 核对 Bucket 地域、当前访问凭证和 CORS。已有访问材料只通过安全入口和发布进程使用，不进入 Git 或 GitHub Actions。
3. 核对本地和 GitHub 已配置的公开资源根地址。发布新版本时递增修订号，重新构建并验证对应目录，保留旧版本。
4. 按 [OSS 资源发布](./oss-resources.md) 上传并验证分卷。同一 Bucket 可用 `--reuse-prefix` 复制旧目录的同名分卷，仍需匿名回读全部内容，再发布最终清单。按版本保存 `complete` 收据。
5. 从真实浏览器验证公开下载、认证解密与缓存，不能用 Node 请求或响应头检查代替。
6. 打包并部署最新轻量 Web，保留回滚版本。验证网页认证、只读文件边界、大厅连接、进程重启复用和已缓存素材的离线读取。完整离线启动按上述独立遗留处理。

当前没有配置多源自动切换，也没有将对象存储上传接入 GitHub Actions。现有构建与发布脚本的用法见 [OSS 资源发布](./oss-resources.md) 和 [资源包说明](./resource-packs.md)。
